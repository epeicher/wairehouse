How Reprint works

Reprint clones an entire WordPress site — files, database, and server configuration — over plain HTTP, in resumable streaming chunks designed to survive the tightest shared-hosting limits. This document maps every block of the repo and the patterns that hold them together.

01What Reprint is

Reprint copies a live WordPress site from a source (a remote site you don't fully control — often locked-down shared hosting) to a target (your laptop, or another host). The whole transfer happens over ordinary HTTP requests against a single WordPress plugin endpoint, so it works even where SSH, direct DB access, and raw PHP execution are blocked.

🖨️

One command

reprint.phar pull https://example.com pulls files + DB + config and starts a local copy you can open in a browser.

⏸️

Resumable everywhere

Every transfer is broken into chunks with a JSON cursor. Interrupt it, re-run the same command, it continues from the last byte.

🪶

Memory & time aware

The server stops a request before hitting the host's memory/time limit and hands back a cursor — never an OOM kill.

The architecture is a textbook producer–consumer split with a streaming pipe between them:

RoleLives inWhat it does
Producer (server)packages/reprint-exporter, shipped as the reprint-exporter-wp WordPress pluginAnswers authenticated HTTP requests by streaming SQL dump fragments and file contents, pausing on a budget and emitting a resume cursor.
Consumer (client)packages/reprint-importer, shipped as reprint.pharA CLI that drives the migration: indexes, diffs, downloads, rewrites URLs, applies the DB, and generates runtime config.
The pipeHTTPmultipart/mixed, gzip-compressed, HMAC-signed, with cursors carried in headers.

04Export side — the producer (server)

The export engine lives in packages/reprint-exporter and runs inside WordPress via the reprint-exporter-wp plugin. Its job: authenticate a request, pick the right producer, and stream a chunked response that can pause and resume.

Why a WordPress plugin, and why ?reprint-api

Many shared hosts (SiteGround, GoDaddy, WP Cloud) block direct PHP execution inside wp-content/plugins/ at the web-server level — a 403 before PHP ever runs. So the plugin doesn't expose its own URL. Instead it routes through WordPress's own front controller, which hosts never block:

  • reprint-exporter-wp/index.php checks $_GET['reprint-api'] (canonical) or the legacy alias $_GET['site-export-api'] at plugin-load time — the earliest interception point a normal plugin gets — and calls _site_export_handle_api_request() then exit.
  • If it's not an API request, it loads the admin settings UI instead (wordpress/site-export.php).

Streaming + database access

GzipOutputStream

Output buffering, zlib.output_compression, and proxy buffering (X-Accel-Buffering: no) are all disabled so a custom incremental gzip stream controls flushing: deflate_add(ZLIB_NO_FLUSH) while writing a part, ZLIB_SYNC_FLUSH at part boundaries. This keeps memory flat regardless of payload size.

Errors become chunks, not 500s

Once the gzip stream is open you can't send an HTTP error code. A global $streaming_context lets the error / exception / shutdown handlers inject an X-Chunk-Type: error part mid-stream instead. The completion chunk is itself wrapped in try/catch so a broken stream is logged, never fatal.

05Import side — the consumer (client)

The importer is a single CLI (reprint.phar) built around the ImportClient class. It has two layers: a set of low-level commands (one network concern each), and a high-level pull orchestrator that chains them.

Command dispatch

The bottom of import.php parses argv, applies legacy aliases (files-sync→files-pull, db-sync→db-pull, …), constructs new ImportClient($url, $stateDir, $fsRoot), and calls run($options), which routes to a run_<command>() method. EXIT_AFTER_IMPORT gates whether the process exits or returns (the latter for the Playground embedder).

Exit codes are the control flow

Because any request can be cut short, the low-level commands don't loop internally. They lean on three exit codes and let the caller (a shell loop, or the pull orchestrator) re-invoke:

✅

0 — complete

state.status === 'complete'. The stage is done.

🔁

2 — partial

Progress was made, call me again. Cursor is saved; the next run resumes.

❌

1 — fatal

An exception bubbled to the bootstrap; a JSON error is written to stderr.

The streaming HTTP client

One primitive does all the networking: ImportClient::fetch_streaming(). It's built on cURL with deliberate choices for hostile networks:

  • No total timeout — a stream can legitimately run 20+ minutes. Instead CURLOPT_LOW_SPEED_LIMIT=1 / LOW_SPEED_TIME=300 detect a genuinely stalled connection.
  • Cursor redundancy — the cursor goes out both as the X-Export-Cursor header and a cursor query param, because some proxies strip custom headers.
  • Browser-mimicking headers — a real-looking User-Agent and Sec-Fetch-* headers, because some WAFs block requests that carry custom auth headers under a non-browser UA.
  • Actionable diagnostics — diagnose_http_error() turns redirects, WAF HTML pages, and JSON error payloads into human messages, and distinguishes a retryable timeout from a hard failure.

MultipartStreamParser — incremental, never buffered

cURL's WRITEFUNCTION feeds bytes into MultipartStreamParser as they arrive. It's a three-state machine — BOUNDARY → HEADERS → BODY — that emits two events: streaming body bytes (large files go straight to disk) and a complete event at each part boundary. It keeps a small tail when a boundary might be split across chunks, and a 64 MB buffer cap catches malformed responses (a WAF page with no boundary).

06The wire protocol

Two design decisions define the protocol: how requests are authenticated, and how responses are framed so they can be split, paused, and resumed.

HMAC authentication

There are no cookies or sessions. Every request is signed with a shared secret using a scheme that survives cURL's unpredictable multipart framing:

signature = HMAC-SHA256( nonce + timestamp + SHA256(body) , secret )   // hex

The signature covers a hash of the body (sent as X-Auth-Content-Hash), not the raw bytes — so for file uploads the client signs the logical content the server can independently reconstruct, regardless of how cURL frames the multipart request. Site_Export_HMAC_Server::verify_globals() checks all four X-Auth-* headers are present, the timestamp is within ±300s (replay window), the nonce is ≥16 chars, and runs every comparison through hash_equals() (constant-time). The secret comes from secret.php (file override, takes precedence) or the site_export_secret WordPress option (set via the admin UI / REST).

multipart/mixed framing

Responses are Content-Type: multipart/mixed; boundary="boundary-<32 hex>", usually Content-Encoding: gzip. Every part declares an X-Chunk-Type and carries chunk-specific headers. Paths are base64-encoded in headers because filesystem bytes aren't guaranteed to be UTF-8.

HeaderDirectionPurpose

Golden rule Producers work with JSON cursor strings. export.php handles base64 for the wire. Never hand a base64 string to a producer constructor — that boundary is a recurring gotcha in the codebase.

07Cursor-based reentrancy

A cursor is a JSON object that encodes complete state — enough to reconstruct exactly where a stream stopped, even if the data underneath shifted between requests. Each producer keeps its cursor as small as it can.

SQL dump cursor

The richest one: current table, PK columns, last PK values, offset, state-machine state, the in-flight row, batch counters, and an oversized-column queue (byte offsets only). Binary string values are wrapped as {"__binary__": base64} for JSON safety.

Column types are re-queried on resume, not stored — the schema can change between requests. If a table was dropped mid-migration, it resets gracefully.

File content cursor

Minimal: {phase, root, path, ctime, bytes} — the last emitted path, its ctime (to detect changes), and the byte offset within the current file. No traversal stack. On resume it re-sorts the path list and binary-searches back to position.

File index cursor

A depth-first stack: {stack: [{dir, after}, …]} — for each directory frame, the last entry processed. Resume re-scandirs and skips past after.

Keyset pagination, not OFFSET

For SQL, resumption uses keyset pagination: build_pk_where_clause() emits an expanded lexicographic comparison (pk₁, pk₂, …) > (last₁, last₂, …). This is O(1) per page regardless of table size. Tables with no primary key fall back to OFFSET pagination (slower, but correct). Oversized column values aren't carried in the cursor at all — only their byte offset — and are re-fetched on demand with SUBSTRING(), keeping the cursor tiny no matter how large a single cell is.

08Resource budgeting

The server's defense against being killed: stop voluntarily, just before the host's limits, and hand back a cursor.

Each non-preflight request builds a ResourceBudget with a start time, a max time (clamped 1–60s, default 5), and a memory ceiling derived from ini_get('memory_limit') times a threshold (clamped 0.1–0.95, default 0.8). Every streaming loop checks $budget->has_remaining() between chunks:

has_remaining():  (now - start) < max_time
              AND  memory_get_usage(true) < max_memory * threshold

When the budget runs out, the loop breaks, the completion chunk reports X-Status: partial, and the cursor rides along. endpoint_sql_chunk goes further: it derives a per-query MAX_EXECUTION_TIME MySQL hint (80% of the time budget) and caps statement size to 80% of the smaller of the client/server max_allowed_packet, so a single query can't overrun the budget or blow the packet limit.

Why this matters On a host with a 30-second max_execution_time and 256 MB memory limit, a naive dumper would get OOM-killed or time-fataled on a large table — losing all progress. Reprint instead returns 200 OK with partial status every few seconds and is asked again. Termination becomes a normal event, not a failure.

10Crash recovery

Resumption isn't just for clean budget stops — it has to survive PHP fatals, OOM kills, SIGINT, and half-written files.

Partial file truncation

State tracks current_file + current_file_bytes (the size after the last saved cursor). On resume, if the file on disk is larger than that — meaning it crashed after writing but before saving — it ftruncates back to the last good byte and re-opens in append mode. The same logic protects db.sql via sql_bytes.

SQL stream crash recovery

In --sql-output=mysql mode, SQL is appended to a .sql-buffer file as it streams. If the transport dies before the completion chunk, the importer saves the cursor, sets status partial, exits 2, and reloads the buffer next run. The finally block deliberately doesn't throw about un-flushed SQL — that would mask the original error.

Atomic state writes

Every state/status/index file is written to a .tmp then renamed, so a crash mid-write never corrupts it. A corrupt .import-state.json on load is renamed aside and the importer starts fresh rather than crashing.

Signals & stall guards

SIGINT/SIGTERM flush the index, save state, then hard-kill the process (curl_close() during an active curl_exec() hangs). A consecutive-timeout guard gives up after 3 timeouts with no cursor progress, so it never loops forever against a dead server.

11Deep dive — MySQLDumpProducer

The SQL exporter is a finite-state machine that yields one fragment per next_sql_fragment() call — a CREATE TABLE, a batched multi-row INSERT (250 rows by default), or a special UPDATE…CONCAT for oversized rows. The whole machine can freeze and thaw on the cursor.

Ten STATE_* constants. The cursor stores which state it's in plus everything needed to re-enter it on the next request.

Values travel as base64

Non-trivial column values are emitted wrapped in FROM_BASE64('…') (or CONVERT(FROM_BASE64('…') USING utf8mb4) for JSON/text). This sidesteps every escaping and character-set hazard in SQL transport — and, crucially, it's the hook the importer's URL rewriter latches onto. The dump remains compatible with standard MySQL import tools.

Oversized rows A single cell larger than the packet budget can't fit in any INSERT. The producer emits a base INSERT with a placeholder, then a queue of UPDATE … SET col = CONCAT(col, FROM_BASE64('…')) statements that append the value in budget-sized slices — re-fetched from the source with SUBSTRING() by byte offset so the cursor stays tiny.

The local index .import-index.jsonl is the memory of what's already on disk; the diff is what makes re-runs cheap.

The delta is a merge-join

diff_indexes_and_build_fetch_list() walks two sorted JSONL indexes with one pointer each, comparing paths:

ComparisonMeaningAction
local < remotepath gone from sourcedelete the local file + index entry
local == remotesame pathif ctime/size/type differ → queue for download

A first-ever sync has an empty local index, so every remote entry becomes a download — a full pull. Progress is checkpointed every 200 entries ({remote_offset, local_after}) so even the diff phase is resumable. Index mutations land in .import-index-updates.jsonl and are merged into the canonical index only on success.

--filter — bring the site up before the uploads land

essential-files downloads code/config/themes/plugins and routes the uploads directory to a skipped list, then marks complete — so you can apply the DB and go live. skipped-earlier later drains that list. The uploads path comes from preflight (uploads.basedir).

Volatile files & preserve-local

If a file changes mid-stream (hash mismatch), it's recorded in .import-volatile-files.json rather than failing. With --on-fs-root-nonempty=preserve-local, anything already on disk — including any symlinked path component — is never overwritten, protecting shared host installs.

13Deep dive — URL rewriting on import

This is the cleverest subsystem. When a site's domain changes, every URL in the database must be rewritten — but those URLs are buried inside serialized PHP, JSON, and block markup where a naive find-and-replace would corrupt length prefixes and break the data. db-apply rewrites them in a single pass, structure-aware, and never calls unserialize().

Format detection is "conservative syntax gate, then try-and-fail." Serialized PHP and JSON recurse, so a URL nested three levels deep inside a serialized array of JSON still gets rewritten.

SqlStatementRewriter — the orchestrator

Owns the per-statement flow. Cheap prefilters reject URL-free statements (the four base64 prefixes aHR0 · dHA6 · dHBz · dHRw cover "http" at every byte alignment). A fast path recognizes the producer's exact INSERT shape with regex and skips the SQL lexer entirely; the slow path lexes once and shares the tokens. It binary-searches a column map so it knows which content type each value is.

PhpSerializationProcessor — the safety net

A cursor parser (no object instantiation, no __wakeup). It reads s:N:"…" by reading exactly N bytes, so embedded quotes and semicolons are safe, and on output it recomputes the byte-length prefix from the rewritten string. A URL that changes length still produces valid serialized data.

Supporting cast

  • StructuredDataUrlRewriter — pre-parses the --rewrite-url mappings once (a hoist that collapsed 94% of db-apply wall time under WASM PHP), detects format, and dispatches leaves to the right processor. Two LRU caches avoid re-rewriting identical values/URLs.
  • Base64ValueScanner — finds FROM_BASE64('…') occurrences (and the CONVERT(… USING utf8mb4) wrapper), decodes lazily, and rebuilds SQL re-encoding only the values that actually changed.
  • SQLitePreparedInsertBuilder — for SQLite targets, replaces values with positional placeholders and binds decoded bytes through PDO, so payload bytes never re-enter SQL text. Caches templates by row "shape."
  • DomainCollector — discovers the source site's own domains/CDN origins from media contexts only (image/video tags and media blocks), so external links in prose don't pollute the --rewrite-url suggestions.

14Deep dive — MySQL query streams

Before rewriting, db.sql must be split into individual statements as it streams in. There are two implementations with an identical contract, chosen for correctness-vs-speed.

WP_MySQL_Naive_Query_Stream

The correctness baseline. Spawns a fresh WP_MySQL_Lexer on every next_query() to find the next top-level semicolon. Accurate, but quadratic in statements per buffer.

WP_MySQL_FastQueryStream — default, ~27× faster

Replaces lexing with a tiny boundary scanner that only understands string literals, backtick identifiers, and comments, using strcspn() to skip "boring" stretches (base64 payloads) at libc speed. A persistent scan cursor resumes partial scans instead of re-scanning.

Graceful fallback The fast stream installs the naive parser and forwards to it the moment it hits something it can't safely handle (a 2 MB buffer with no top-level ;, or an unterminated construct at end-of-input). It logs the switch to the audit log and keeps bytes_consumed monotonic so resume still works. Speed by default, correctness as a guaranteed floor.

WpcloudHostAnalyzer

Detects WP Cloud / Atomic by the __wp__ directory, WP at doc_root/__wp__/, and the PRIVACY_MODEL env var. Strips the Memcached object-cache.php and wpcomsh mu-plugins, finds auto_prepend_file directories, and declares a thumbnail-generator route — because WP Cloud exports ship only full-size uploads, so missing -WxH sizes are generated on the fly with GD before WordPress even boots.

Plugin deactivation, derived from the manifest

Any paths_to_remove entry under wp-content/plugins/ also triggers removal from the active_plugins option at the end of db-apply — while the DB connection is still open. This avoids "plugin file does not exist" warnings without firing deactivation hooks into code that's already gone from disk. SiteGround strips sg-cachepress and sg-security the same way.

Two route handlers are inlined into the generated runtime.php: the WP Cloud thumbnail generator, and a remote upload proxy that streams missing uploads straight from the source while files-pull is still running — so the site looks complete before the media library finishes downloading.

Stages 4–6 are conditional: db-apply only with a DB target, flat-docroot only with --flatten-to, start only when the runtime is launchable in-process.

Two mechanisms make it seamless:

  • run_until_complete() wraps each network stage in a loop (up to 1,000 iterations): if a stage returns partial (exit 2), it resets status and retries — turning the per-request resume protocol into a single smooth stage from the user's point of view.
  • Resume + delta — Pull reads the last completed stage from state.pull.stage and skips ahead. If the previous pull already completed, prepare_repull() sets up a delta: it keeps the local index and preflight, clears the transfer state, and deletes the dump + remote index so they're re-fetched. Re-running pull after success just syncs what changed.

18Distribution & the Playground UI

Two artifacts ship, plus a browser-based wizard that runs the importer entirely client-side.

reprint.phar

Built by Box (bin/build-reprint-phar.sh + box.json). The version comes from git tags into a baked-in VERSION file. The bundled sqlite-database-integration submodule is compiled in, so the phar is self-contained and needs no MySQL on the target. A single CLI guard keyed on IMPORTER_PHAR_ENTRY / IMPORTER_WRAPPER_ENTRY / IMPORTER_WEB_ENTRY lets the same file run as a phar, a source wrapper, or an embedded include.

reprint-exporter-wp.zip

The WordPress plugin, with the exporter Composer package vendored in. stamp-plugin-version.sh stamps the plugin version into index.php + lib.php. The admin UI (Site_Export_Plugin) manages the HMAC secret via a WP option exposed over REST, so platforms can provision it programmatically.

The Playground wizard (reprint-ui/)

A WordPress.com → Playground handoff that runs the migration in the browser and never touches site bytes server-side. It's a stateless PHP app (signed, encrypted cookies — no sessions): the user authorizes via WP.com OAuth, the server enables the exporter and rotates a 60-minute HMAC secret on the chosen Atomic site, then hands off to playground.wordpress.net with a generated Blueprint. Inside Playground, reprint-import.php includes the same reprint.phar and runs pull … --target-engine=sqlite --runtime=none — the browser is the network transport, Playground is the server, and a uploads-proxy mu-plugin streams missing media from the source until the sync completes.

19Key takeaways

⏸️

Resumption is the spine

Cursors, exit code 2, budgets, atomic state, truncation-on-resume — every layer assumes any request can stop at any moment.

🔌

One narrow interface

Everything goes through one HMAC-signed multipart endpoint on a WordPress plugin — the lowest common denominator that works on locked-down hosts.

🧩

Pluggable seams

PDO adapters, host analyzers ↔ runtime appliers (via a data manifest), and naive ↔ fast query streams are all swappable behind stable contracts.

📈

Adapts to the host

AIMD tuning and resource budgeting mean the same binary runs well on a 256 MB shared host and a beefy server without configuration.

🔒

Structure-preserving rewrites

URL rewriting walks serialized PHP / JSON / block markup without unserialize(), recomputing length prefixes — correctness over shortcuts.

🚀

Multiple targets, one path

MySQL, SQLite, nginx, PHP built-in server, and browser Playground all reuse the same import engine.
